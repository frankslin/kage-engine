# prototype/ — 拼字法造字工具

一個「用簡單拼字法造字」的互動原型：載入 GlyphWiki 上的任何字，點選部件刪除，
搜尋任意部件插入、微調外框，輸出可直接提交 GlyphWiki 的 KAGE 資料字串。

## 使用方式

直接用瀏覽器開啟 `prototype/index.html`（雙擊即可，`file://` 下可運作）。
**需要網路**——字形資料是即時透過 GlyphWiki API（`glyphwiki.org/api/glyph`，
CORS 開放）抓取的，本頁不內嵌任何字形資料。

示範流程（啟動時從 20 個複雜結構字中隨機載入一個當例子；以「槲」為例）：

1. 載入「槲」→ 畫布上點左邊的「木」（紅色高亮，組成列清單同步）。
2. 按「刪除選取的部件」。
3. 在搜尋框輸入「食」→ 列出 GlyphWiki 上實際存在的位置變體
   （`u98df-01` 左偏形、`-02`、`-04`、`-j/-g/-t/-k/-v` 地區形⋯⋯）。
4. 點縮圖插入——外框自動沿用剛刪除部件的位置。
5. 微調位置：選取的列（可多選，含手繪筆畫列）會顯示紅色虛線聯合外框——
   **框內拖曳＝整體移動**；單選一個部件時另有**八個縮放把手**（也支援觸控），
   或用滑桿精確輸入 x1/y1/x2/y2，兩者即時同步重新渲染。
   原地點一下外框可取消選取。
6. 「依位置排序」按鈕把組成列重排成閱讀順序（同一橫排從左到右，否則從上到下）。
   排序依據是**實際渲染的筆墨範圍**而非 99 外框——偏旁形部件（`-01`/`-02` 等）
   的外框常大量重疊，用外框排會錯。
7. 所有修改（刪除/插入/替換/拖曳/縮放/滑桿/排序/重設）都會進歷史棧，
   「復原上一步」按鈕或 ⌘Z／Ctrl+Z 可逐步回退（上限 100 步；
   一段連續滑桿或拖曳只記一筆；載入新字會清空歷史）。
7. **不知道部件叫什麼名字時用手寫搜尋**：在「手寫搜尋部件」的方框裡直接寫，
   每寫完一筆就重搜一次，點縮圖即插入（與上面的搜尋是同一套流程）。
   搜尋範圍是 GlyphWiki 全部 36 萬個字形，**筆順不影響結果**。
   照平常的筆畫寫就好（「口」3 畫）——KAGE 資料把橫折存成兩個筆畫元素，
   「自動拆轉角」會替你補上這一刀，切點標紅圈。詳見頁面上的「寫法要點」。
8. 底部輸出框隨時是完整 KAGE 資料，「複製」後可直接貼進 GlyphWiki 的字形編輯框
   （所有部件參照都是 GlyphWiki 上真實存在的部件名）。

## 開發與部署

**開發**：先在專案根目錄跑一次

```bash
npm install
npm run build:dist    # src/*.ts → dist/kage.js
```

之後直接雙擊開啟 `prototype/index.html` 即可（`file://` 下可運作，已實測）——
它以 `../dist/kage.js` 引用引擎 bundle（rollup 打的 IIFE，只在 global scope
定義 `Kage`，故頁面裡有一行 `var Polygons = Kage.Polygons;`）。改動 `src/*.ts`
後要重跑 `npm run build:dist` 才會反映到頁面上。
引擎架構見 [`doc/WALKTHROUGH.md`](../doc/WALKTHROUGH.md)。

**部署**：跑 `sh build-dist.sh` 組裝 `dist/`——腳本會先呼叫根目錄的
`npm run build:dist` 確保 bundle 最新，再把**壓縮版**複製進
`dist/engine/kage.min.js`、把 `index.html` 的引用改寫成目錄內路徑
（並驗證改寫確實發生、沒有殘留 `../` 引用），最後複製 `vendor/gwtegaki/`
（手寫搜尋模型，含其 MIT LICENSE）。
把 **`dist/` 的內容**整個上傳到任何靜態伺服器（GitHub Pages/Cloudflare
Pages/nginx）即可。`dist/` 是建置產物，已被 `.gitignore` 排除。

開發頁引用未壓縮的 `../dist/kage.js`（可讀、可下中斷點），部署則用
`kage.min.js`：**34 KB vs 124 KB**，也比換引擎前的 8 個檔合計（101 KB）小三分之二。
兩者輸出逐位元組相同——terser 預設不改屬性名，所以 `Kage.Polygons`、
`getEachStrokes` 這些頁面用到的名稱都在（已實測 dist 版全流程）。

## 實作要點

- **手寫搜尋（gwtegaki）**：模型來自 [`kurgm/gwtegaki`](https://github.com/kurgm/gwtegaki)
  （MIT，作者與 kage-engine 同一人），見 [`vendor/gwtegaki/README.md`](./vendor/gwtegaki/README.md)。
  分工是：**特徵抽取（394 維向量）在本機由 WebAssembly 算完**，只有向量會 POST 到
  gwtegaki 的 Cloud Run 後端做近似最近鄰（HNSW），後端只回字形名，
  縮圖仍由本頁自己的 kage 引擎畫——所以手寫結果跟「插入部件」共用
  `renderCandList` / `insertComponent`，連明朝／黑體切換都自動跟著走。
  幾件實作上會踩到的事：
  - wasm 用 `--target no-modules` 建置、位元組以 base64 內嵌，才能在 `file://` 下運作。
  - 初始化走非同步的 `wasm_bindgen()` 而非 `initSync()`：Chrome 禁止主執行緒
    同步編譯 4 KB 以上的 wasm，這支有 26 KB。
  - 特徵值要過一次 `Math.fround`（上游前端也是），索引是以 f32 建的。
  - 每寫完一筆就重搜，用遞增序號擋掉過期回應。
- **自動拆轉角**（本 fork 自己加的，gwtegaki 沒有）：KAGE 的資料把「橫折／豎折」
  這種硬折存成**兩個**筆畫元素——`u53e3-j`（口）是 4 行不是書法上的 3 畫——
  而 gwtegaki 的特徵向量對筆畫數很敏感，照中文習慣寫 3 畫幾乎必定落空。
  但「豎彎鉤／臥鉤」這種圓轉又只算一個元素（七、匕、心），所以不能見角就拆。
  做法是先 RDP 簡化（eps 3）濾掉手抖的偽轉角，再在轉向 ≥ **75°**、
  且兩側線段都 ≥ 12 單位的頂點切開。
  - 75° 是實測選的：45〜65° 會把「七」的豎彎鉤切開，反而找不到。
  - 有拆到角時**兩種切分都送、按距離合併**，拆錯了原樣的結果仍在榜上；
    沒拆到角就只送一次，不白白多打上游一次請求。
  - 切點在手寫板上標紅圈，讓人看得見發生了什麼；真的拆錯可以把開關關掉。
  - 實測（真實滑鼠、含手抖）：口寫 3 畫 → `u53e3-j` 距離 0.00；關掉開關後
    `u53e3` 直接掉出候選。日 4 畫 → `u65e5-g` 0.71，田 5 畫 → `u7530-var-001` 1.49，
    山 3 畫 → `u5c71-g` 2.48。
  - 模型的 `MODEL_VERSION` 必須等於後端索引的 `v`，對不上後端直接回 404。
  - 後端閒置會休眠，第一次搜尋可能要等 20〜30 秒（上游自己也標記為待改善）。
- **預覽字體切換（明朝／黑體）**：畫布上方的 serif/sans 開關只換渲染方式，
  輸出的 KAGE 資料完全不變（字形資料與字體風格無關，GlyphWiki 兩種都會渲染），
  所以它**不進 undo 棧**。實作上只有 `newKage()` 一個收口
  （`kage.kShotai = kage.kGothic`），畫布、組成列、替換候選縮圖都走它因此自動跟著切；
  搜尋結果的縮圖不在 `render()` 範圍內，用 `lastSearchFound` 記住上次命中的名稱重畫。
  用途是校對：明朝體的 `adjust*` 自動微調會**掩蓋**拼字問題（鱗會自動縮小、勾會自動
  避讓），黑體沒有任何微調、筆畫粗細均勻，部件沒擺正會看得更清楚。
- **部件選取**：用 `Kage.makeGlyph3()`（逐筆回傳 `Polygons`）搭配
  「每個頂層資料列展開後的筆畫數」把渲染結果分區對應回資料列，
  既保留全字層級的明朝體微調（`adjust*` 系列在完整筆畫集上執行），
  又能知道每個多邊形屬於哪一列、支援點選。
- **別名解參照**：GlyphWiki 上 `uXXXX` 常常只是指向 `uXXXX-j` 等的全框別名
  （單一 `99:` 列、外框 0:0:200:200），載入時自動追到真正有組成列的那層。
- **部品遞迴抓取**：`99:` 參照的部品逐層抓齊後才渲染，記憶體內快取避免重複請求。
- **變體探測**：搜尋部件時自動嘗試 GlyphWiki 的位置變體命名慣例
  （`-01`〜`-14`、`-j/-g/-t/-k/-v/-jv`），只列出實際存在者。

## 部件庫與替換候選（components.js）

`components.js` 由 `build-components.py` 從兩個資料來源離線生成：

1. **GlyphWiki 完整資料傾印**（`dump.tar.gz` 內的 `dump_newest_only.txt`）：
   統計每個字形被 `99:` 參照的次數，收錄 ≥50 次、排除個人空間（名稱含 `_`）的
   3,127 個常用部件，並依 `u+碼位` 命名慣例歸戶到 1,492 個字元
   （`u6728-01` → 木）。
2. **char-components 專案的 `vt.json`**（`../char-components/web/data/vt.json`）：
   853 筆方向安全的單向異體映射（扌→手、氵→水、朩→木⋯⋯），
   把不同寫法的部件連到同一個抽象字元。

這份資料支撐三個功能：

- **插入部件搜尋**：輸入漢字（打字自動搜尋，400ms 防抖）即合併列出
  GlyphWiki 位置變體探測結果與本地常用部件庫的命中項，
  **以渲染結果為指紋簡併同形變體**（如「田」12 個變體只剩 6 種實際不同的形狀），
  按鈕只顯示字形縮圖（名稱在滑鼠提示中）。
- **替換候選**：單選一個部件時，自動列出「同字元的其他位置變體 +
  vt 異體字元的部件」，點縮圖**保留外框原地替換**——例如選中 `u624c-01`（扌）
  會列出 `u624b-01`（手）等候選，這正是「把某部件換成另一種寫法」的一鍵操作。
- **組成列標注**：部件列顯示對應的字元（「部件 木 u6728-01」），不用心算碼位。

重新生成：

```bash
python3 build-components.py <dump_newest_only.txt> [vt.json]
```

## 已知限制（原型階段刻意從簡）

- 非 `99:` 參照的手繪筆畫字，選取粒度是單筆筆畫，還沒有框選/群組。
- 尚未接異體部件候選（`vt.json` 反查之類的 Tier 1 資料來源）。
- 沒有「展開部件」功能（把 `99:` 列攤平成筆畫做更細的編輯）。
- 插入的部件不支援 `99:` 列的伸縮參數（sx/sy），只有外框四值。
